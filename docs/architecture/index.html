Happy, from process to pixel.

A source-backed guide to the system that lets a person run coding agents on a computer and control them from mobile, web, desktop, or automation—without giving the server plaintext access to the conversation.

01 / Mental model

The shortest useful explanation

Happy separates where an agent runs from where a person supervises it. The local machine remains the execution environment; the backend coordinates encrypted state and commands between authenticated clients.

Happy is an encrypted control plane for local coding-agent processes.
“Control plane” here means identity, discovery, presence, message sequencing, state synchronization, and command routing—not execution of the coding agent itself.
Runs locally

Agent execution and tools

Claude, Codex, Gemini, and OpenClaw runners execute on the user’s machine through the Happy CLI/daemon. Filesystem and shell access stay beside the repository.

Coordinates centrally

Encrypted state and routing

The server authenticates clients, stores opaque encrypted content, assigns sequence numbers, tracks presence, and relays realtime updates and RPC calls.

02 / Topology

One control plane, several edges

The architecture is hub-and-spoke for coordination, but agent execution remains at an edge machine. Three Socket.IO connection scopes keep account-wide, session-specific, and machine-specific traffic distinct.

03 / Surfaces

Runtime responsibilities

The repository contains more than “frontend + backend.” Each executable surface has a distinct ownership boundary.

Remote console

  • Zustand client state
  • REST bootstrap + user-scoped realtime
  • Native, web, and Tauri targets
Execution owner

Happy CLI + daemon

  • Provider normalization

Happy Server

Fastify and Socket.IO provide authentication, domain APIs, persistent update sequencing, presence, RPC routing, integrations, and metrics.

Automation client

04 / Core flow

A remote agent turn, end to end

Durable messages use HTTP and persistent update events; live control uses Socket.IO RPC. The client’s outbox and sequence cursors make the UI resilient to reconnects and retries.

01 · Compose

The app adds a local outbox item, encrypts message content with the session key, and prepares a stable local ID.

02 · Persist

The app posts encrypted messages to the v3 session endpoint. The server allocates per-session and per-account sequence numbers.

03 · Fan out

The server emits a durable update to user-scoped clients and the interested session-scoped process.

04 · Execute

The local runner decrypts the prompt, drives the provider, normalizes provider events, and publishes encrypted agent output.

05 · Reconcile

The app decrypts updates, deduplicates by IDs/sequences, reduces messages into view state, and clears matching outbox entries.

05 / Sync & RPC

Two traffic classes share one socket

Normal state fan-out and point-to-point RPC both use /v1/updates, but have different delivery semantics. Durable updates can be recovered by refetching; RPC requires a live handler owner.

Durable + ephemeral fan-out

EventRouter

Persistent update events describe database-backed mutations. Ephemeral events carry presence, thinking, usage, and session status. Recipient filters map to Socket.IO rooms.

  • user:<userId>
  • user:<userId>:user-scoped
  • user:<userId>:session:<sessionId>
  • user:<userId>:machine:<machineId>
Point-to-point control

RPC handler rooms

Handlers register a prefixed method in rpc:<userId>:<method>. Calls are forwarded to a live target, acknowledged, and encrypted with session- or machine-specific keys.

  • Session methods: <sessionId>:<method>
  • Machine methods: <machineId>:<method>
  • Reconnect grace before “not available”

Connection state recovery is intentionally disabled in the current server configuration. On a non-recovered reconnect, the app invalidates and refetches state through REST. Redis streams currently provide cross-replica Socket.IO delivery, not client-side replay.
06 / Trust boundary

The server routes what it cannot read

Happy’s most important architectural boundary sits before transport. Client-held secrets encrypt session messages and state; the backend operates on ciphertext and the minimum metadata needed for coordination.

Trusted client edge

Plaintext exists here

  • Prompt and agent response content
  • Session and machine metadata
  • Agent state and tool details
  • Artifact and KV values
  • Session/machine data keys
encryption boundary
Coordination core

Server-visible material

  • Account, session, and machine IDs
  • Sequence numbers and timestamps
  • Presence and routing scope
  • Encrypted blobs and wrapped data keys
  • Operational metadata and integration tokens
Legacy encryption

NaCl secretbox

XSalsa20-Poly1305 with a 24-byte nonce and 32-byte shared secret. The wire blob is nonce followed by authenticated ciphertext, then base64 encoded.

Data-key encryption

AES-256-GCM

A versioned payload uses a 12-byte nonce, ciphertext, and 16-byte auth tag. The content key is separately wrapped with an ephemeral NaCl box keypair.

End-to-end encryption protects user content, not all metadata. IDs, ownership relationships, timestamps, versions, presence, and usage/account fields remain available to the server because they are required for indexing, routing, billing, or operations.

09 / Deployment

Hosted and portable modes

The same server domain logic can run as a multi-service hosted deployment or as a self-contained distribution with an embedded database and bundled web app.

Hosted

Multi-replica service

Node runs Fastify + Socket.IO against external Postgres. Redis streams distribute room traffic between replicas. S3-compatible object storage handles files. Prometheus metrics are exposed separately.

  • Docker and Kubernetes manifests
  • nginx routes API and file domains
  • Redis required for cross-replica realtime
Self-host / portable

Single distribution

The standalone entry point can run migrations and serve using PGlite in a local data directory, local file storage, and an optional bundled Happy web app served by Fastify.

  • happy-server migrate
  • happy-server serve
  • Redis optional
  • HTML config injection for the bundled SPA

10 / Observations

What the shape of the code says

These are architectural interpretations from the current source, not product commitments.

The encryption boundary is the organizing principle.

It explains why rich domain objects are reconstructed in clients, why the server stores opaque strings/bytes, and why RPC payloads pass through the backend without server-side interpretation.

The app sync layer is a de facto client domain service.

Sync coordinates encryption keys, REST fetches, realtime subscriptions, outboxes, pagination, purchases, artifacts, friends, and notifications. It is powerful, but it concentrates many reasons to change in one long-lived singleton.

Realtime correctness falls back to durable APIs.

Sequence numbers, idempotent local IDs, version checks, and REST invalidation after reconnect form the recovery model. The socket is a low-latency signal path, not the sole source of truth.

There are two desktop strategies.

The Happy App reaches desktop through Tauri around the Expo web target. Codium is a separate Electron architecture with its own renderer, IPC contracts, workers, plugin host, and storage. They should be treated as distinct products until their responsibilities intentionally converge.

Protocol unification is incomplete by design.

happy-wire says the newer session envelope is frozen and not the production path; legacy role-based message content remains active. The architecture should not imply that every provider already speaks one canonical event model.

Standalone mode is more than a deployment toggle.

PGlite, local files, static SPA serving, configuration injection, and optional Redis create a materially different operational topology that deserves its own testing and documentation path.
